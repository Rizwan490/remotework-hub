# RemoteWork Hub — static remote jobs platform

A complete, production-ready remote / work-from-home job board built with **HTML5, CSS3, vanilla JavaScript and a JSON data file**. No framework, no build step, no backend, no paid libraries, no external API. Deploys to Cloudflare Pages by uploading the folder.

---

## 1. What's in the box

```
/

├── jobs.html             Search + filter interface (sidebar on desktop, drawer on mobile)

│
├── remote-jobs/          GENERATED: one static HTML page per job (tools/build.js)

│                         canonical, Open Graph tags and JobPosting structured data
├── categories.html       All categories with live job counts

├── about.html

├── privacy.html
├── terms.html
├── disclaimer.html
├── 404.html
│
├── assets/
│   ├── css/
│   │   ├── style.css         Design tokens, base, layout, header, hero, footer
│   │   ├── components.css    Buttons, cards, badges, filters, states, ads, overlays
│   │   └── responsive.css    Mobile-first breakpoints + drawer/bottom-nav behaviour

│   │   ├── jobs.js           Data loading, normalising, card + detail rendering, schema
│   │   ├── search.js         Client-side keyword + location search
│   │   ├── filters.js        Listing engine: filters, sort, URL sync, load more
│   │   └── ui.js             Page controllers, drawer, share, accordion
│   ├── data/
│   │   └── jobs.json         ← EDIT THIS: the only file you touch to add jobs
│   └── images/               favicon.svg, og-default.png, app icons
│
├── tools/
│   └── build.js              Static job page generator (plain Node, no dependencies)
│
├── site.webmanifest
├── robots.txt
├── sitemap.xml               GENERATED by tools/build.js — includes every job URL

└── README.md
```

**One change from the requested structure:** `config.js` lives at `assets/js/config.js` (the spec mentioned `js/config.js` in one place and `assets/js/config.js` in another). Everything is under `assets/` so the root stays clean. Three extra files were added because they materially help: `saved.html` (the saved-jobs page the spec asked for "if practical"), `_headers` (Cloudflare security + caching, no build step needed) and `site.webmanifest`.

Script load order is fixed and matters: `config → ads → app → jobs → search → filters → ui`. All scripts use `defer`, so nothing blocks rendering.

## 2. Local testing

`jobs.json` is loaded with `fetch()`, which browsers block on `file://` URLs. **Open the site through a local server, not by double-clicking index.html.**

```bash
# Python (already on macOS/Linux)
cd remotework-hub
python3 -m http.server 8080
# → http://localhost:8080

# or Node
npx serve .

# or VS Code: install "Live Server", right-click index.html → Open with Live Server
```

What to click through: home → a category → a job → Save → the bookmark icon in the header → Saved jobs. Then `jobs.html`, tick some filters, and check the URL updates.

## 4. Cloudflare Pages deployment

**Option A — connect the repo (recommended, auto-deploys on every push)**

1. Cloudflare dashboard → **Workers & Pages** → **Create** → **Pages** → **Connect to Git**.
2. Authorise GitHub and pick your repository.
3. Build settings:
   - Framework preset: **None**
   - Build command: *(leave empty)*
   - Build output directory: `/`
   - Root directory: `/` (or the subfolder if the site isn't at the repo root)
4. **Save and Deploy.** You get `https://your-project.pages.dev`.

**Option B — direct upload:** Workers & Pages → Create → Pages → **Upload assets** → drag the folder in.

**Option C — build on Cloudflare instead of committing generated files:** set the
build command to `node tools/build.js` and the output directory to `/`. Only worth it
if you would rather not commit `remote-jobs/`.

### What is actually free

| | Cost |
|---|---|
| Hosting on Cloudflare Pages | Free — unlimited bandwidth, 500 builds/month, custom domains included |
| `your-project.pages.dev` subdomain | Free, permanent, HTTPS included |
| A custom domain (`example.com`) | **Not free** — roughly $10–15 a year from any registrar. Cloudflare only charges you the wholesale price, but it is never zero. |

So the site goes live for free on `*.pages.dev`. That subdomain is a perfectly good
home: it is fast, it has valid HTTPS and Google indexes it normally. Buy a custom
domain later if you want one — moving is a 5-minute job (see below), and nothing in
the code is tied to the old address.

### After the first deploy — point the site at its real URL

The domain is written into canonical tags and `sitemap.xml`, so it has to be set once:

1. `assets/js/config.js` → `url: 'https://your-project.pages.dev'` (no trailing slash).
2. `robots.txt` → the `Sitemap:` line.
3. Rebuild and push:

```bash
node tools/build.js
git add -A && git commit -m "Set live domain" && git push
```

Cloudflare redeploys on the push. Do exactly the same three steps later if you move to
a custom domain — in that case add it first under project → **Custom domains** → *Set
up a domain*.

`404.html` is served automatically by Cloudflare Pages for unknown paths — no
configuration needed. `_headers` and `_redirects` are applied automatically too.

## 5. How to add a job

Edit **`assets/data/jobs.json` only**. Nothing else needs touching — every page picks new jobs up automatically.

```json
{
  "id": "acme-support-2026-04",
  "demo": false,
  "title": "Remote Customer Support Specialist",
  "company": "Acme Inc",
  "companyLogo": "",
  "location": "Remote (US)",
  "country": "United States",
  "remote": true,
  "jobType": "Full-time",
  "category": "customer-service",
  "experience": "Entry Level",
  "salary": "$45,000 – $55,000 / year",
  "salaryMin": 45000,
  "salaryMax": 55000,
  "salaryCurrency": "USD",
  "salaryPeriod": "YEAR",
  "postedDate": "2026-04-18",
  "validThrough": "2026-06-18",
  "description": "One or two sentences describing the role.",
  "responsibilities": ["...", "..."],
  "requirements": ["...", "..."],
  "benefits": ["...", "..."],
  "skills": ["Zendesk", "Live Chat"],
  "applyUrl": "https://employer.example.com/careers/123",
  "source": "Employer careers page",
  "featured": false,
  "status": "active"
}
```

| Field | Notes |
|---|---|
| `id` | Must be unique — it ends the job's page URL (`…-acme-support-2026-04.html`). Changing it changes that URL, so old links and rankings are lost. |
| `slug` | Optional. Overrides the generated URL slug when you want to write the URL yourself. |
| `category` | Must match a `slug` in `CATEGORIES` in `config.js`. |
| `jobType` / `experience` | Must match `FILTER_OPTIONS` in `config.js` or the filters won't catch it. |
| `salary` | Free text, shown to visitors. |
| `salaryMin` / `salaryMax` | Numbers, **annualised**, used for salary filtering and sorting. Set `0` when the employer publishes no salary. |
| `salaryCurrency` / `salaryPeriod` | `"USD"`, and `"YEAR"` / `"MONTH"` / `"HOUR"`. Only used for structured data, and only when real. |
| `postedDate` / `validThrough` | `YYYY-MM-DD`. |
| `applyUrl` | Must be `http(s)`. Anything else is rejected and the apply button shows as unavailable. |
| `featured` | `true` floats it to the top of the default ordering and onto the home page. |
| `status` | Anything other than `"active"` hides the job everywhere. |
| `demo` | `true` adds a "Demo" badge and suppresses structured data for that listing. |

**After every edit to `jobs.json`, rebuild the job pages:**

```bash
node tools/build.js
```

Without that step the new listing appears in the search and category listings (those
read `jobs.json` in the browser), but it has no page of its own for Google to index.

**Going live with real listings:**

1. Replace every entry in `jobs.json` with verified listings (`"demo": false`).
2. Set `demoMode: false` in `assets/js/config.js`.
3. Run `node tools/build.js`.

That switch removes the demo banner, removes the site-wide `noindex`, and enables
JobPosting structured data on every generated page.

**Validate your JSON before deploying** — one stray comma stops every listing from loading:

```bash
python3 -m json.tool assets/data/jobs.json > /dev/null && echo "valid"
```

Adding a **category**: append an object to `CATEGORIES` in `config.js` (`slug`, `name`, `icon`, `blurb`, `intro`). `icon` must be a key in the `ICONS` map in `app.js` — `headset, calendar, table, pen, megaphone, palette, code, trending, wallet, clipboard, book, heart, sparkles, rocket, briefcase, globe`.

## 6. Static job pages (`node tools/build.js`)

Every listing in `jobs.json` gets its own real HTML file so each job can be indexed,
shared and ranked on a URL of its own:

```
https://your-domain/remote-jobs/remote-customer-support-specialist-at-acme-inc-acme-support-2026-04.html
```

Run it whenever `jobs.json` or the domain in `config.js` changes:

```bash
node tools/build.js
```

Node 14+ is enough. Nothing is installed, nothing is bundled — the script only writes
HTML. It is safe to run any number of times.

**What each run does**

| Output | Detail |
|---|---|
| `remote-jobs/<slug>.html` | One page per active listing, fully rendered server-side: `h1`, description, responsibilities, requirements, benefits, skills, apply block, job summary and related jobs are all in the HTML before any JavaScript runs. |
| Per-page SEO | Unique `<title>` and meta description, self-referencing canonical, `robots` with `max-image-preview:large`, Open Graph `article` tags (published time, expiry, section, skill tags) and a Twitter summary card. |
| Structured data | `JobPosting` (title, HTML description, dates, employment type, remote location type, applicant country, salary range, skills, qualifications) plus a `BreadcrumbList`. |
| `sitemap.xml` | Rewritten with every job URL and its `postedDate` as `lastmod`, alongside the home, listing, category and legal pages. |
| `_redirects` | Sends `/remote-jobs/` (the folder itself) to the main listing page. |
| Cleanup | Pages for listings that left `jobs.json` are deleted. Only files carrying the generator's marker comment are ever removed, so hand-written files in that folder are safe. |

**Where the settings live** — `assets/js/config.js`:

```js
jobPages: {
  dir: 'remote-jobs'    // folder + first URL segment
},

seo: {
  cleanUrls: true       // canonical/sitemap URLs drop the .html
}
```

The script reads your brand, domain, categories and feature switches from that same
file, so there is no second place to keep in sync.

### Why `cleanUrls` matters

Cloudflare Pages serves every page without its extension and **redirects**
`/jobs.html` → `/jobs`. A canonical tag pointing at `/jobs.html` would therefore point
at a redirect, which wastes the signal. With `cleanUrls: true`:

| | Form used |
|---|---|
| Canonical, `og:url`, JSON-LD, `sitemap.xml`, `_redirects` | `/remote-jobs/<slug>` — the address Cloudflare actually serves |
| `href` inside the site (nav, cards, breadcrumbs) | `remote-jobs/<slug>.html` — the real file, so the folder still works when opened locally or over `python3 -m http.server` |

Set it to `false` only if you move to a host that serves `.html` as-is.

**How the pages behave for visitors**

The generated HTML is the complete page. The site's JavaScript then takes over the
same markup to add the things that cannot be pre-rendered: save/unsave, share buttons,
recently viewed and ad slots. With JavaScript disabled the job still reads perfectly
and the apply link still works.

**Old links keep working.** `job.html?id=…` looks the listing up and sends the visitor
to its generated page. That page is `noindex`, so the two URLs never compete for the
same job in search. If a listing is in `jobs.json` but the build has not been run yet,
`job.html` notices the missing file and renders the job itself as a fallback.

**Structured data is never invented.** A listing marked `"demo": true`, or missing a
title, company or posted date, gets a full page with no `JobPosting` markup. Feeding
Google markup for jobs that do not exist is what gets sites penalised, so the build
prints a count of those pages instead of filling the gaps.

**Deploying:** run the script before you push, and commit the `remote-jobs/` folder
along with `sitemap.xml` and `_redirects`. Cloudflare Pages needs no build command —
it just serves the files. If you prefer to build on deploy instead, set the build
command to `node tools/build.js` and the output directory to `/`.

## 7. How to change branding

Everything lives in `assets/js/config.js` → `SITE_CONFIG`:

```js
name: 'RemoteWork Hub',        // every logo, footer, title and legal page
shortName: 'RWH',
url: 'https://your-domain.com', // canonical + Open Graph URLs are rewritten to this
description: '...',
contactEmail: 'you@your-domain.com',
```

Nothing is hard-coded — the HTML uses `data-site-name`, `data-contact-email`, `data-year` placeholders that `app.js` fills in, and canonical/`og:url` tags are rewritten to match `url` at runtime.

**Colours and typography:** `assets/css/style.css` → the `:root` block. Change `--color-primary` and the whole site follows — buttons, badges, links, focus rings, hero glow, logo mark.

**Logo:** the mark is an inline SVG in the header/footer of each HTML file (`.brand__mark`), plus `assets/images/favicon.svg`. Swap in your own SVG or drop an `<img>` in its place.

**Social image:** replace `assets/images/og-default.png` (1200×630).

## 8. How to add ad network code

Ads are **off by default**. Nothing renders and no slot reserves space until you switch them on.

Open `assets/js/ads.js`:

```js
const ADS_CONFIG = {
  enabled: true,
  provider: 'adsterra',        // 'adsense' | 'adsterra' | 'hilltopads' | 'custom'
  header:  '<script ...></script>',   // paste publisher code here
  inline:  '',
  sidebar: '',
  footer:  '',
  mobile:  '',
  adsense: { client: 'ca-pub-XXXXXXXXXXXXXXXX' },  // AdSense only
  showLabel: true,
  inlineEvery: 6              // an inline slot after every 6 job cards
};
```

Slot placement already built into the pages:

| Key | Where |
|---|---|
| `header` | Below the navbar on the home page, and at the top of the job detail |
| `inline` | Between job cards on listing pages (every `inlineEvery` cards) |
| `sidebar` | Job detail sidebar, under the share card |
| `footer` | Above the footer on home/jobs, and at the bottom of the job detail |
| `mobile` | Reserved for a mobile-only unit — add `<div class="ad-slot" data-ad="mobile"></div>` where you want it |

**Adsterra / HilltopAds:** copy the whole snippet from your dashboard and paste it as the string. Script tags are re-created so they execute.
**AdSense:** set `provider: 'adsense'` and `adsense.client`; the loader script is injected once, and your `<ins class="adsbygoogle">` block goes into the slot string.

Slots fill lazily as they scroll near the viewport, so ads never slow the first paint. The code refuses to produce pop-unders, auto-clicks, forced redirects, hidden units or buttons that imitate an apply button — every filled slot carries an "Advertisement" label.

## 9. How to change SEO configuration

Per page, in the HTML `<head>`: `<title>`, `meta description`, `link rel=canonical`, Open Graph and Twitter tags are all present and unique. Edit them directly.

Site-wide, in `config.js`:

```js
seo: {
  titleTemplate: '%s | RemoteWork Hub',  // %s = the page title
  defaultImage: 'assets/images/og-default.png',
  twitterHandle: '@yourhandle',
  locale: 'en_US'
}
```

`job.html` and `category.html` generate their title, description and canonical URL at runtime from the data, via `RW.setMeta()` in `app.js`.

**Structured data:** `JobPosting` JSON-LD is generated in `jobs.js` → `jobPostingSchema()`, on individual job pages only — never on search or category pages. It is emitted only when `demoMode` is `false` and the listing isn't flagged `demo`. Optional properties (`baseSalary`, `validThrough`, `employmentType`, `applicantLocationRequirements`) are **omitted when the data is missing rather than invented**. The home page carries `WebSite` + `SearchAction` JSON-LD.

Also update: `robots.txt` (sitemap URL) and `sitemap.xml` (all `<loc>` values).

## 12. Features implemented

- Live search across title, company, category, description, location and skills — case-insensitive, whitespace tolerant, URL-driven (`jobs.html?q=customer+service&location=remote`).
- Filters: keyword, location, category, job type, experience, salary band, remote-only, sort (relevance / newest / oldest / salary / A–Z). All client-side, no page reload, synced to the URL, with live option counts and removable filter chips.
- Desktop sidebar filters; mobile slide-in drawer with a backdrop, Escape-to-close and focus handling.
- Job detail with responsibilities, requirements, benefits, skills, sticky sidebar summary, share row (Web Share API where supported, plus Facebook / X / LinkedIn / WhatsApp / copy link) and a mobile sticky apply bar.
- Apply button always states that it leaves the site: **"Apply on Employer Website"**, opened with `rel="noopener noreferrer nofollow"`. External redirects are never disguised.
- Save jobs and recently-viewed, both in `localStorage`, no account, surviving refresh, with a counter badge in the header and bottom nav.
- Related jobs scored by category, job type, experience, country and shared skills.
- Skeleton loading, an empty state with "Clear Filters", and a retryable error state. JavaScript errors are never shown to visitors.
- Accessibility: skip link, landmarks, one `<h1>` per page, labelled controls, `aria-pressed` / `aria-expanded` / `aria-live`, visible focus rings, 44px+ touch targets, `prefers-reduced-motion` respected.
- Security: every JSON value is escaped before rendering; apply and logo URLs are validated as `http(s)` before use; all external links get `rel="noopener noreferrer"`; no auto-downloads, pop-unders, fake notifications or deceptive redirects.

## 15. Honest limitations

- **No server.** The contact form opens your email client; the newsletter form stores nothing until you connect a provider. Both say so on the page rather than pretending otherwise.
- **The job pages are generated, not live.** `/remote-jobs/` is only as current as the last `node tools/build.js` run. Forget the rebuild and the new listing still shows up in search and category listings, but has no page of its own. The search, filter and category pages stay client-rendered — they are listings, and each result links to a static page.
- **Slugs are tied to the `id`.** Change a listing's `id` (or its title or company) and it gets a new URL; the old one 404s and loses whatever ranking it had. Keep ids stable, or set an explicit `slug`.
- **Saved jobs are per-browser.** No sync across devices without a backend.
- **The demo listings are fictional.** They exist to test the interface and carry no application links. Replace them before launch.
